## ⚠️ Risky changes (behaviour changes — please review)

### 1. `2143fb5` fix(network)!: typed API errors, close error responses, broader connectivity check

Files: `model/api/CustomInterceptor.kt`, `utils/Exceptions.kt`, `utils/Util.kt`, `res/values/strings.xml`.

| | Before | After |
|---|---|---|
| Non-2xx response | Threw `UnknownException(response.message)` without closing the response. That leaked the connection, and the message is empty on HTTP/2. | Response is closed, then `ApiException(code, message)` is thrown |
| Error text | Often blank | 401/403: "API key is missing or invalid"; 429: rate-limit message; 5xx: "service unavailable"; other codes: "Request failed (HTTP n)" |
| DNS failure, connection refused, timeout | Raw exception text, e.g. "timeout" or "Failed to connect to api.nytimes.com/…" | `NoConnectivityException` ("Please check your internet connection") |
| Connectivity check | Only Wi-Fi, cellular or Ethernet counted as online | Any active network with `NET_CAPABILITY_INTERNET`, so VPN, USB and Bluetooth tethering now count as online |
| Exceptions | Mutable `var message` | Immutable; cause is kept; `UnknownException` removed |

**Tests:** new `CustomInterceptorTest` with 10 tests (MockWebServer + Robolectric). It covers:
- the key param
- the 401/429/5xx/404 mapping
- the offline path
- VPN-only counting as online, and Wi-Fi without internet counting as offline
- DNS failure, refused connection, and timeout mapping (cause kept)
- Retrofit converter parsing

**What to check:**
- The new error wording is acceptable to you.
- On a device, airplane mode shows the internet message, and an invalid key shows the API-key message.
- The broader online check is OK. It's still a pre-check: a captive portal counts as online and then fails with a real error, same as before.

**Revert:** `git revert 2143fb5`. This also reverts its test.

### 2. `3f80121` fix(viewmodel)!: rethrow cancellation, ignore duplicate retries

File: `viewmodel/PopularVM.kt`.

- **Before:** `runCatching { }` around the suspend call swallowed `CancellationException`, so a cancelled fetch could be reported as an error. Every `retry()` tap launched another parallel request, and the requests raced on `uiState`.
- **After:**
  - `try`/`catch` rethrows cancellation.
  - `retry()` does nothing while a fetch is already running.
  - Only typed errors (`NoConnectivityException`, `ApiException`) pass their localized message to the UI. Any other exception, such as a JSON parse error from a captive-portal HTML page, produces a blank message, so the screen shows only "Unable to load articles".
- **Tests:**
  - two retries during an in-flight fetch call the repository exactly once
  - a typed message passes through
  - an untyped exception message is hidden
- **What to check:**
  - You're fine with a Retry tap during loading being ignored. In practice the button isn't visible while loading, so this only matters for fast double taps.
  - You're fine that unexpected errors show only the generic text. Raw exception text no longer reaches users, so there's less to debug from screenshots.
- **Revert:** `git revert 3f80121`

### 3. `275f16c` ui(error)!: show error cause inline, drop duplicate snackbar

File: `ui/screens/PopularListScreen.kt`.

- **Before:** the error screen showed the generic "Unable to load articles" and the actual cause appeared only in a transient snackbar, which was often blank.
- **After:** the cause is shown under the title in the error screen, and the snackbar is removed. The error block is a polite live region, so TalkBack still announces the failure the way it announced the snackbar.
- **Tests:**
  - `error state shows the error cause inline`
  - the error block is a polite live region, and a blank cause shows only the generic text
- **What to check:**
  - the look of the error screen (toggle airplane mode before launching)
  - with TalkBack on, the failure is announced
- **Revert:** `git revert 275f16c`
